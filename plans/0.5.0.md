# ddigraph 0.5.0 — "Make RDF real"

## Context

ddigraph advertises five graph backends. It ships one. `src/ddigraph/` contains
exactly one adapter (`schema/neo4j_adapter.py`); RDF, Gremlin, NetworkX and pandas
exist only as `demo/load_*.py` scripts that are excluded from both wheel and sdist
(`pyproject.toml` `[tool.check-manifest].ignore`). The README's "Multi-backend
support — Neo4j, RDF/SPARQL, Gremlin, NetworkX, and pandas" (README.md:26) describes
demos, not code.

The RDF story is the worst of it, and also the most valuable to fix. Today there is
no agreed vocabulary: four different `ddi:` namespaces are in play across
`demo/load_rdf.py:52`, `docs/en/backends/rdf.md:38`, `:101`, and
`demo/sdmx_from_physical_instance.py:553` — and three predicate conventions
(`ddi:hasConstruct` in the doc's mapping table at rdf.md:271, `ddi:HAS_CONSTRUCT` in
the same doc's SPARQL at rdf.md:206, `ddi:question_text` in the demo). Neo4j
relationship names and Python attribute names are leaking straight into RDF
predicate space. Any output produced this way is uninteroperable.

0.5.0 fixes this properly: one documented, versioned vocabulary aligned to the
DDI Alliance's own published RDF standards; a first-class `ddigraph export` so the
semantic-web audience never has to write Python; SKOS/XKOS for code lists; SHACL
shapes derived from the schema that already exists; RDF as an input format for
round-tripping; and `ddigraph preview` so you can see what you loaded without
opening Neo4j Browser.

Three decisions were taken up front:

- **Vocabulary**: DISCO/SKOS-aligned hybrid — reuse published standards where a term
  exists, mint one project namespace for the rest.
- **Scope**: all seven items, including RDF as an input format.
- **Export scope**: unify all three DDI flavors behind one node/edge seam.

### Corrections to the original brief

- **`rdflib` is already an optional extra**, not a hard runtime dependency
  (`pyproject.toml:70-84`), and `tests/test_extras_lazy_imports.py:63` already
  enforces that no `src/` module top-level-imports it. That part of the audit is
  done. The real offender is **`xmlschema>=3.4`**, a core dependency with zero
  imports anywhere in `src/` — used only by `scripts/generate_schema_definitions.py`,
  which is not shipped in the wheel.
- **`schema/definitions.py` is not the single source of truth.** Both it and the
  `schema/definitions/` package are git-tracked; Python resolves the package first,
  so the 102 KB module is unreachable dead code that still ships in every wheel. The
  live source of truth is `schema/definitions/`.
- **0.5.0 already carries a committed breaking change**: removal of
  `ddigraph ensure-schema` and `ensure-fragment-schema`, announced twice in
  CHANGELOG.md:181-189 and :262-268.

## Honest scope

Two things in this release cannot be done as cleanly as they sound.

**Round-tripping is only lossless because we make it so.** The DISCO/SKOS mapping is
many-to-one: `Question` and `QuestionItem` both map to `disco:Question`;
`CodeScheme`, `CodeList` and `CategoryScheme` all map to `skos:ConceptScheme`. A
reader cannot recover the original label from the standard type alone. The fix is to
**always emit two `rdf:type` triples** — the standard one for interop, and the
project-namespace one for identity:

```turtle
<urn:ddi:ie.cso:q-4711:1.0.0>
    a disco:Question , ddigraph:QuestionItem ;
    skos:prefLabel "Main activity status"@en-IE .
```

Interop consumers read `disco:Question` and ignore the rest; the reader reads
`ddigraph:QuestionItem` and round-trips exactly. This is idiomatic RDF, not a hack,
but it is the reason item 5 is tractable at all and it must not be optimised away.

**The vocabulary namespace is versioned independently of the package.** The obvious
choice, `…/ns/0.5/`, would change on every minor release and break every consumer —
precisely the problem this release exists to fix. The namespace is
`https://pbisson44.github.io/ddigraph/ns/1.0/`, frozen at v1.0 and changed only on a
breaking vocabulary change. It resolves: the docs site is already published at that
host, so `docs/en/ns/1.0.md` plus a served `vocabulary.ttl` makes it dereferenceable.

**~230 of ~250 node labels get project-namespace terms.** DISCO covers 16 classes.
The curated alignment table is worth hand-writing for the ~20 high-value concepts
(Study, Variable, Question, Universe, DataFile, Concept, Category, CodeList, …);
everything else is derived mechanically from `DDISchema`. Do not attempt to
hand-align all 250.

## The keystone: one graph view across three flavors

Everything else in this release depends on this and it should land first.

The three DDI flavors currently have three unrelated intermediate representations,
and only Codebook has a backend-neutral view:

| Flavor | Parser entry | IR | Neutral view |
| --- | --- | --- | --- |
| Codebook | `parse_ddi_batches()` (`ingest/loader.py:1965`) | `DDIBatch` | `DDIIngestGraph.nodes()/.relationships()` (`schema/ddi_graph.py:215,308`) |
| Lifecycle | `DDIFragmentParser(path).parse_batches()` (`ingest/fragment_loader.py:479`) | `FragmentBatch` | none |
| CDI | `parse_cdi_batches()` (`ingest/cdi_loader.py:773`) | `CDIBatch` | none — parse-only, no writer |

Reuse the existing `Node` and `Relationship` dataclasses (`schema/ddi_graph.py:68,77`)
— do not invent new ones. Add **`src/ddigraph/graph/view.py`**:

```python
@dataclass(slots=True)
class GraphChunk:
    nodes: list[Node]
    relationships: list[Relationship]


def iter_graph(
    path, *, flavor=None, dataset_id=None, dataset_name=None, chunk_size=200, recover=True
) -> Iterator[GraphChunk]: ...
```

`iter_graph` detects the flavor via the existing `detect_ddi_format`
(`ingest/fragment_loader.py:1300`) and dispatches:

- **Codebook** — wrap each `DDIBatch` in `DDIIngestGraph.from_ddi_batch()` and drain
  the existing generators. Nearly free.
- **Lifecycle** — `parse_batches()` is two-phase: phase 1 yields node-only batches,
  phase 2 yields relationship-only batches (docstring at `fragment_loader.py:482`).
  Build a `node_key -> element_type` map as phase-1 chunks stream past; phase 2 then
  has every label it needs to construct `Relationship` endpoint stubs. The phase
  ordering guarantees the map is complete before the first edge arrives.
- **CDI** — `CDIRelationshipRecord` already carries `source_label`/`target_label`
  (`ingest/cdi_loader.py:87`), so this is a direct field mapping.

This also ends DDI-CDI's parse-only status for every read path in the release.

> Watch out: two different classes are named `RelationshipDefinition` —
> `schema/definitions/_dataclasses.py:36` (exported, never instantiated) and
> `schema/ddi_graph.py:425` (drives all real edge building). The second is the live one.

### 2. The vocabulary

New **`src/ddigraph/rdf/vocabulary.py`**. Namespace URIs and mapping tables are
**plain strings with no `rdflib` import**, so the tables stay importable without the
extra and are directly testable.

```python
DDIGRAPH = "https://pbisson44.github.io/ddigraph/ns/1.0/"
DISCO = "http://rdf-vocabulary.ddialliance.org/discovery#"
XKOS = "http://rdf-vocabulary.ddialliance.org/xkos#"
SKOS = "http://www.w3.org/2004/02/skos/core#"
DCTERMS = "http://purl.org/dc/terms/"
```

Curated alignment (the hand-written part):

| ddigraph label | Standard class | ddigraph label | Standard class |
| --- | --- | --- | --- |
| `Study`, `StudyUnit` | `disco:Study` | `Concept` | `skos:Concept` |
| `Variable` | `disco:Variable` | `Category` | `skos:Concept` |
| `RepresentedVariable` | `disco:RepresentedVariable` | `CodeScheme`, `CodeList` | `skos:ConceptScheme` |
| `Question`, `QuestionItem` | `disco:Question` | `CategoryGroup` | `xkos:ClassificationLevel` |
| `Universe` | `disco:Universe` | `Instrument` | `disco:Instrument` |
| `DataFile` | `disco:DataFile` | `Group`, `Series` | `disco:StudyGroup` |
| `LogicalRecord` | `disco:LogicalDataSet` | *(~230 others)* | `ddigraph:<Label>` |

Predicates — curated where a standard term exists, mechanical otherwise. The
mechanical rule is `SCREAMING_SNAKE -> lowerCamelCase` (`USES_CODELIST` →
`ddigraph:usesCodeList`), which is what the doc's mapping table always claimed and no
code ever did. There is no existing case-conversion helper in the repo; write one.

| Relationship | Predicate | Property | Predicate |
| --- | --- | --- | --- |
| `USES_CONCEPT` | `disco:concept` | `label` | `skos:prefLabel` / `rdfs:label` |
| `ASKS_QUESTION` | `disco:question` | `description` | `dcterms:description` / `skos:definition` |
| `USES_CODELIST` | `disco:responseDomain` | `code` | `skos:notation` |
| `HAS_CATEGORY` | `skos:inScheme` (inverse) | `urn` | `dcterms:identifier` |
| `IN_DATASET` | `dcterms:isPartOf` | `agency` | `dcterms:publisher` |
| *(default)* | `ddigraph:<lowerCamel>` | `external_references` | `skos:exactMatch` |

Subject IRIs use the DDI URN when present — `urn:ddi:<agency>:<id>:<version>`, already
computed as `Fragment.node_key` (`fragment_loader.py`) and precedented in
`demo/sdmx_from_physical_instance.py:605` — falling back to `{--base-uri}/{label}/{id}`.
This is agency-neutral and globally unique without inventing a domain. Do **not**
repeat `demo/load_rdf.py:72`'s colon-flattening, which destroys the URN.

`language` fields become literal language tags (`"…"@en-IE`), not predicates.

### 3. `ddigraph export`

**`src/ddigraph/export.py`** (format dispatch). `rdflib` is imported **inside


then `set_defaults(handler=_export_command)` (`cli.py:515-647`). Add `export` to the
supported tier of the public API in `__init__.py`, and to `tests/test_public_api.py`.

### 4. SKOS for code lists

Handled inside `rdf/writer.py` as a special case over the generic mapping. For every
`CodeScheme`/`CodeList`/`CategoryScheme` node emit `skos:ConceptScheme`; for every
`Category` emit `skos:Concept` with `skos:inScheme`, `skos:prefLabel` (language-tagged
from the record's `language` field), `skos:notation` from `code`, and
`skos:definition` from `description`. `CategoryRecord` and `CodeSchemeRecord`
(`ingest/loader.py:339,317`) already carry every field needed — including
`external_references`, which becomes `skos:exactMatch` and is the actual hook for
joining to EuroVoc, DBpedia and other external vocabularies.

### 5. RDF as an input format

New **`src/ddigraph/rdf/reader.py`**: `read_graph(path, format=None) -> Iterator[GraphChunk]`.
Inverts the vocabulary tables, keying node identity off the project-namespace
`rdf:type` (see *Honest scope*). Because it yields `GraphChunk`, it plugs into every
consumer built above at no extra cost — including `ddigraph load out.ttl`, which
makes the round trip real:

```text
survey.xml --export--> out.ttl --load--> Neo4j
```

Accept Turtle, JSON-LD, N-Triples and RDF/XML (rdflib sniffs by extension).

### 6. SHACL shapes

New **`src/ddigraph/rdf/shacl.py`**: `shapes_graph(...)` derived from
`DDISchema.get_all_nodes()` and `FRAGMENT_RELATIONSHIP_TYPES`. This follows the
existing precedent in `schema/definitions/__init__.py:79-129` almost exactly —
`generate_constraint_queries()` and `generate_index_queries()` already walk
`get_all_nodes()` and emit target-language text; SHACL is the same walk with a
different emitter.

Per `NodeDefinition`: one `sh:NodeShape`, `sh:targetClass` from the vocabulary map,
`sh:property` for `id_field` (`sh:minCount 1; sh:maxCount 1`) and one per entry in
`properties`. Per relationship: `sh:property` with `sh:path` and `sh:class`.

New CLI verb — shapes derive from the schema, not from a document, so folding this
into `export` would need a fake input file:

```bash
ddigraph shapes -o shapes.ttl [--flavor lifecycle|codebook|cdi]
```

### 7. `ddigraph preview`

New **`src/ddigraph/preview.py`**, consuming `GraphChunk`.

```bash
ddigraph preview survey.xml --format mermaid
ddigraph preview survey.xml --format html -o preview.html
```

Preview the **schema shape**, not every node — the demo corpus runs to 65 MB and a
per-node diagram is unreadable. Emit label→label edges with instance counts, plus
node and relationship count tables. The `html` output must be self-contained with no
external assets (offline use, and it matches how the docs already treat mermaid via
`pymdownx.superfences`); render the diagram as inline SVG rather than loading
mermaid.js from a CDN. `--limit N` samples concrete instances.

## Appendix — separately found defects

Found while planning, all reproduced against `origin/main` with the dev extras
installed. None is caused by the work above; they are listed so they can be scheduled
independently. The full suite passes (`pytest`: 359 passed, 3 skipped, 82.6% coverage)
and `mypy .` is clean, so these are gaps in what is checked, not regressions.

### B1 — `NEO4J_*` silently overrides `DDIGRAPH_NEO4J_*` (highest priority)

`config.py:26-42` lists `AliasChoices("NEO4J_URI", "DDIGRAPH_NEO4J_URI")`. `AliasChoices`
is first-match-wins, so the legacy prefix beats the one the class docstring calls
"preferred" — on all four credential fields (uri, user, password, database):

```text
DDIGRAPH_NEO4J_URI=bolt://PREFERRED:7687 NEO4J_URI=bolt://LEGACY:7687
  -> Settings().neo4j_uri     == "bolt://LEGACY:7687"
  -> resolve_credentials_source() == "DDIGRAPH_* variables"     # wrong
```

`resolve_credentials_source` (`config.py:192-196`) checks `DDIGRAPH_*` first and so
reports the opposite of what was used. For a tool whose main verb writes to a
database, a stale `NEO4J_URI` in a shell or `.env` silently redirects the write and
the diagnostic confirms the wrong target. `tests/test_config.py:49-50` only tests the
two prefixes in isolation, never together, so the suite passes.

Fix: put `DDIGRAPH_*` first in every `AliasChoices`, make
`resolve_credentials_source` report the winner, and add a both-set precedence test.

### B2 — `ruff check .` fails on `origin/main`

```text
D301 Use `r"""` if any backslashes in a docstring
  --> demo/audit_graph_standalone.py:2:1
```

Reproduced on a clean `origin/main` checkout, and with both ruff 0.16.2 and the
0.15.13 pinned in `.pre-commit-config.yaml` — so it is not version drift. `ruff check .`
is a blocking CI gate and `demo/` is not in any ruff exclude (only mypy excludes it,
`pyproject.toml:170`). One-character fix: `r"""` on the module docstring.

### B3 — Bootstrap errors advertise a removed environment variable

`graph/bootstrap.py:92` and `:134` tell the user to "supply the correct database via
DDIGRAPH_NEO4J_DATABASE (legacy compatibility alias: NEO4DDI_NEO4J_DATABASE …)".
`config.py:156-158` states `NEO4DDI_*` is "deprecated and ignored as of 0.4.0. The
recognition shim was removed." The error message sends users to a variable that does
nothing.

### B4 — A codebook-only bootstrap creates 77 DDI-CDI constraints

`bootstrap_queries()` (`graph/bootstrap.py:33`) passes `include_fragments`
*positionally* to `generate_all_schema_queries(include_fragments, include_cdi)`, so
`include_cdi` keeps its `True` default and is never reachable:

```text
bootstrap_queries(include_fragments=False) -> 154 queries, 77 of them CDI-labelled
  e.g. CREATE CONSTRAINT ... FOR (n:CDIConcept) REQUIRE n.cdi_id IS UNIQUE
```

Half of every codebook bootstrap creates schema for a format that has no writer at
all. Thread `include_cdi` through, or document that bootstrap is deliberately
all-flavors.

### B5 — The bundled DDI-C `codebook.xsd` is not valid XSD

`schemas/ddi-c/codebook.xsd:695` puts `<xs:simpleType>` before `<xs:annotation>`
inside an `<xs:attribute>`; XSD requires `(annotation?, simpleType?)`. Both libxml2
(via lxml) and `xmlschema` 1.0 and 1.1 refuse to compile it. DDI-L 3.3 is fine —
`instance_3_3.xsd` compiles in 0.8 s.

This is an upstream defect in the vendored file (`manifest.json` fetches it from
`ddialliance/ddi-c_2` master), not a ddigraph bug, but it falsifies the promise in
`resources.py:19-23` that the bundled schemas let consumers "validate XML against the
official XSDs directly from an installed distribution" — that only holds for DDI-L.
`scripts/xsd_coverage.py` is unaffected because it reads the XSD as plain XML with
`etree.parse` rather than compiling it as a schema.

### B6 — The main DDI-L test fixture is not valid DDI-L 3.3

`tests/fixtures/fragment_instance.xml` fails validation against the bundled
`instance_3_3.xsd`: `Instrument` does not accept `id`/`agency`/`version` there, and
`InstrumentName` is not an allowed child. This does not make the loader wrong — the
fixture is hand-written and minimal — but it matters for the golden-file tests
proposed above, since exporting from a non-conformant fixture bakes non-conformant
structure into the snapshots. Validate fixtures before freezing any golden file.

### Feature candidates not in the seven

- **`ddigraph validate`** — the package already bundles every official XSD and
  `resources.schemas_root()` exists precisely to expose them, but no command
  validates anything. lxml is already a core dependency, so DDI-L validation costs
  no new dependency. Blocked for DDI-C by B5 until the vendored file is patched or
  the loader falls back. This would also give `xmlschema` a real job instead of being
  the unused core dependency it is today.
- **A DDI-CDI write path** — CDI parses (209 entities), has 32 curated
  `NodeDefinition`s, and gets constraints created at bootstrap (B4), but
  `api.aload` raises `NotImplementedError` for it and the CLI `--format` has no `cdi`
